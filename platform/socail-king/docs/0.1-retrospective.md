## 2 Real Issues Caught During Rollout (Verification Bypass Patterns)

**两条都是"framework 自己差点犯它要治的病"** — verification gap during the rollout of a verification framework。Meta-讽刺但反过来证明了 framework premise 是对的:**verification gap 发生在『验证用的 path』跟『要保护的 path』不一致的时候**。

### Issue 1: migration 文件放错目录(sandbox path ≠ framework path)

**Symptom**:
- 用户 reload SM 后 prod `supermatrix.db` 仍是 schema_version 22
- 5 张新表全部不存在
- spawn API 收到 `verification_predicate` 字段会静默 fail(底层表都没有)

**Root cause**:
- codexroot 0.1 batch-1 把 3 个 `.sql` 放在 `/Users/LOCAL_USER/SuperMatrix/migrations/`(repo 根)
- Migration framework 读 `/Users/LOCAL_USER/SuperMatrix/src/adapters/store-sqlite/migrations/`(022 等历史 migration 都在这)
- `applyMigrations` Pass 2 处理 `.opt.sql` 时 failure = degraded 不 throw,所以 boot 时静默失败,看不见

**Why review didn't catch**:
- codexroot 的 review pack 写 "Migration sandbox apply OK"
- Sandbox apply 用的是 fresh DB + 手动 load 文件,**不走 framework path resolution**
- YOLO supervisor 9 个 evaluation criteria 里有 "tests pass" 但没 "prod path verify"
- 787 个测试全过(因为测试用的也是 sandbox path)

**Detection**: SK reload 后用 `lsof` 看 SM PID 打开的 DB + `sqlite3 schema_version`,挖出 23/24/25 没 apply。

**Fix**: codexroot hotfix `b36c300` `git mv` 到正确目录 + 删空的 `/migrations/` 根目录。

**Lesson**: **"Sandbox apply ≠ Production apply"**。0.2/0.3+ 每个 framework migration 必须 post-reload 通过 `lsof + schema_version + 表存在性`验证,不能只看 sandbox。

### Issue 2: fp warning self-cascade(递归 blind spot)

**Symptom**(预测,1.0 切换前若不修必发生):
- 0.1 spawn API warning path:caller 缺 / 错 `verification_predicate` → `emitFpPredicateWarning()` spawn first-principle
- 这个 warning spawn 本身**没有** `verification_predicate`
- fp 收到 warning 调用 handler → 又触发一次 warning → cascade
- 0.1-0.3 warn 模式下静默 cascade,1.0 strict 4xx 模式下 warning 通道直接断,fp 拿不到任何 warning

**Root cause**:
- `emitFpPredicateWarning()` 在 `apiServer.ts:271-303` 调用内部 `/api/spawn` 但没补 predicate
- 设计时只考虑"让 warning 流到 fp",没想"warning spawn 自己也得遵守 contract"

**Why review didn't catch**:
- 评审聚焦 "warning flow 通不通"(通了,fp 收得到)
- 没问 "warning spawn 自己是否 comply with 它在 warn 的 contract"

**Detection**: fp 接 SK 委托做 inventory dashboard 时,自己 grep `apiServer.ts:271-303` 发现这条是 A 类 highest-priority call_site。

**Fix(Phase 1 by fp dashboard,ETA 本周)**: codexroot 给 warning spawn 加 `inbox-message` template predicate(design doc §FP warning path L599-613 已给模板)。

**Lesson**: **"Framework verification primitives must verify themselves"**。任何"enforcing predicate contract"的 code path 自身必须 comply,否则形成 recursive blind spot。

## 共同 pattern

**两个 issue 共享同一根因**: verification via a path different from the path under test。

- Issue 1: sandbox path 验证 ≠ framework path 实际跑的
- Issue 2: warning-emitting path 没遵守它自己 enforce 的 rule

**这正是整个 0.1-1.0 framework 要治的用户级病**(supermap 假成功 = A 自己脑补 verify 路径 ≠ 真实 verify 路径)。在 framework 自己 rollout 期间命中两次同款病,反讽地证明了 framework premise 是对的。

## 建议沉淀到 console-principles.md(spawn first-principle review)

新增 "Verification Discipline" 章节,两条规则:

1. **Sandbox apply ≠ Production apply**:framework 改动落 prod 后必须通过实际运行环境的 path resolution 验证(`lsof` / 真实 schema query / 真实 endpoint hit),不能只看 sandbox/test path。
2. **Self-compliance**:发出 verification warning / enforce contract 的 code path 自身必须 comply with 它在 enforce 的 contract,否则形成 recursive blind spot。
